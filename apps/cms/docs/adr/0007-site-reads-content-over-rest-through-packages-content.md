# apps/site reads content over HTTP through `@workspace/content`, and live data from the Property Feed

apps/site never imports Payload or connects to the database. It reads CMS content through `packages/content`, a module whose interface is domain queries (`getProperty`, `searchProperties`, `getCuratedList`, `getPage`…). Internally it calls the CMS REST API using the Payload SDK and a read-only credential scoped to one Site. Live Availability, Quotes and checkout come from the Property Feed through a separate module (`packages/feed-client`, or a module in apps/site until a second consumer exists). The generated `payload-types.ts` lives in `packages/cms-types` (generated by apps/cms, committed), and both apps and `packages/content` import from there.

## Considered Options

- **Local API through a shared package.** Rejected. apps/site would bundle the whole Payload config and need database credentials. With one site deployment per Site (ADR-0010), every deployment would then hold credentials that can read every Client's data.
- **Raw REST calls in apps/site.** Rejected. Query building, Site scoping, draft handling, depth and caching would leak into every page. `packages/content` keeps them behind a small interface.
- **The CMS proxies Feed calls.** Rejected. It adds a hop and a failure point to the latency-sensitive search and quote path, for no content benefit.

## Consequences

- Each site deployment's credential can read only its own Site, and only published content. Site deployments never read Drafts: Preview is drawn by the CMS (ADR-0018).
- The queries in `packages/content` run over a small client seam. apps/site uses the HTTP adapter. The CMS preview uses a Local API adapter as the Staff User, so both get the same Site-facing shapes. apps/site itself still never imports Payload.
- Date search is a merge: the Feed returns the matching Feed IDs, and `packages/content` supplies the CMS content for them. That merge lives in one module, not in pages.
- Pure, framework-free pieces that apps/cms also needs, such as the cache-tag vocabulary and the Curated List rule compiler, are exported from `@workspace/content/shared` so that apps/cms doesn't pull in the site's Next-specific code.
- `@payloadcms/sdk` is young. If it falls short, we swap it for `fetch` + `qs-esm` inside `packages/content` without changing callers.
